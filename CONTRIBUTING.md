# Contributing

This repository is part of **[Forenly AI Lab](https://github.com/Forenly-AI-Lab)**, an open-source contribution program.

## Before anything else — what this is not

This is **not employment, an internship, or a trial period.** There is no salary, no assigned work, no deadlines, and no minimum commitment.

Nobody here will hand you a task. You pick an issue that interests you, you work on it if and when you want to, and you stop whenever you like. That is not a formality — it is the arrangement.

**You keep the copyright to your contribution.** Nothing is transferred to Forenly AI. Your work stays public under this repository's Apache 2.0 license and your name stays on the commit.

If your university requires a signed internship agreement or insured-internship paperwork, this program cannot provide it.

If you are on a student visa or a residence permit outside your home country, please check your own status before contributing. Even unpaid open-source work can matter for a permit.

## Picking something to work on

Issues carry a level label. It is there so **you** can find a starting point — it is not a filter, and nothing is assigned based on it.

| Label | What the work looks like |
|---|---|
| `level:explorer` | Run something, read something, write down what happened |
| `level:contributor` | A small pull request — a fix, a test, a tooling improvement |
| `level:research` | Reproduce a published result, or investigate why it cannot be reproduced |

Pick one. Comment on it if you want to talk it through first — you do not have to.

## How to contribute

1. Fork the repository.
2. Work on your fork, in a branch.
3. Open a pull request.

That is the whole process. There is no CLA to sign: under [Apache 2.0 §5](LICENSE), a contribution you deliberately submit for inclusion is licensed under the same terms as the repository, and GitHub's terms say the same thing for public repositories.

## What a good contribution looks like here

This is a reproducibility repository, so the standard is different from ordinary software work.

**Report what happened, not what should have happened.** A reproduction that fails is a result. A number that does not match the published one is a result. Both are more useful than a report that quietly omits them.

**Record your environment.** Operating system, Python version, and the exact versions of every relevant package. In this repository the environment *is* the finding — the same command produces different outcomes on different dependency stacks, and without the versions a number means nothing.

**Say what you are unsure about.** "I got 41% and I do not know why" is a good contribution. "I got 41%" with no context is not.

**Do not paper over a failure.** If a script crashes, do not wrap it in a try/except and move on. Find out where it breaks, and write that down.

## Review

Pull requests are reviewed the way any open-source maintainer would review them: technical feedback on the change, no deadlines, no obligation on your side to act on it.

If a review goes quiet, ping the pull request. That is not rude.

## Credit

Merged contributions are credited on GitHub under your own name — that is the permanent record.

For a merged contribution we can also issue a written statement naming what you did, for example *"Reproduced and documented the Diffusion Policy PushT evaluation benchmark."* It points at the pull request; the pull request is the real thing.
